# ezcontrol

在 Windows 运行机上启动一个小服务器，用浏览器登录后即可远程查看屏幕、操作键鼠、传文件。单个 exe，约 1.6 MB，无运行时依赖。

## 功能

- **看屏幕**：
  - 有显卡时用 DXGI 桌面复制采集，只复制 Windows 报告变化的区域，屏幕不变时几乎不占 CPU。
  - 无显卡的虚拟机/云主机自动改用 Windows.Graphics.Capture，避免 DXGI 在软件渲染下卡顿。
  - 只编码变化的 64×64 区块，SIMD JPEG 多核并行编码，帧率上限可选 5–120fps。实际帧率不会超过运行机显示器的刷新率。
  - 帧缓冲在采集与各观看端之间共享，不做整帧拷贝。
  - 可调画质、分辨率缩放、帧率；画面静止后自动发送一次高清补帧，文字更清晰。
  - 缩放默认「自动」：按浏览器里实际显示的像素大小编码，窗口缩放时跟着变。看不出差别，但编码 CPU 和带宽都省很多。
  - 支持多显示器切换。
- **低延迟**：浏览器每画完一帧才确认（ACK），服务器最多 2 帧在途——网络慢时自动降帧而不是积压延迟；键鼠事件与画面编码分开处理，不会被编码阻塞
- **键鼠**：鼠标（左/中/右/侧键、滚轮、拖拽）；键盘按扫描码发送，与远端键盘布局无关；全屏时用 Keyboard Lock 捕获 Win、Alt+Tab、Esc 等系统键（Chromium 内核浏览器）
- **虚拟键盘**：完整键盘＋功能键、方向键、媒体键；修饰键点一次=一次性按住，再点=常按，再点=松开
- **快捷键菜单**：任务管理器、Alt+Tab、Win+D/E/R、截图、Alt+F4、复制粘贴等，也可自定义组合，如 `Ctrl+Shift+T`
- **文本输入**：把一段文字（含中文、emoji）直接打到远端光标处，无需远端输入法
- **剪贴板双向同步**（仅文本，在「剪贴板」面板设置，按浏览器记住）：
  - **远程复制 → 本机**：运行机上复制后，约 0.3 秒内推送到浏览器。
  - **本机复制 → 远程**：切回网页时（以及网页在前台时每秒）检测本机剪贴板变化。在远程按 Ctrl+V 时也会先同步本机内容。
  - 每个方向可选「直接同步」「提示后同步」「关闭」，默认提示后同步；同步过的内容不会来回反弹。
  - 读取本机剪贴板需要浏览器授权，要求 HTTPS 或 localhost：经 Cloudflare 隧道访问是 HTTPS，首次会弹出授权。纯 http 的局域网 IP 访问时，本机→远程只能手动同步。
  - 也可以在面板里手动读取、写入远程或本机剪贴板。
- **文件**：浏览所有磁盘，下载、上传（拖拽、多文件、进度、分块上传可过 Cloudflare 100MB 限制）、新建文件夹、改名、删除
- **触屏**：点按=左键，长按=右键，单指拖动=拖拽，双指滑动=滚轮
- **安全**：
  - 默认只监听 127.0.0.1；密码用 PBKDF2-SHA256 加盐哈希保存
  - 会话 Cookie 为 HttpOnly、SameSite=Strict
  - 同一 IP 连续输错 5 次锁定 1 分钟，之后锁定时间逐次加倍
  - 同源检查和 CSRF 头校验
  - 控制台记录登录、会话、文件操作日志

## 使用

```bash
ezcontrol.exe
```

首次运行会在 exe 旁生成 `ezcontrol.json`，并在控制台打印一次初始密码（用户名 `admin`）。浏览器打开 http://127.0.0.1:8090 登录。

修改密码：

```bash
ezcontrol.exe --set-password
```

其他选项见 `ezcontrol.exe --help`：`--port`、`--bind`、`--user`、`--capture`、`--bench`。

> 建议**以管理员身份运行**：否则无法操作以管理员权限运行的窗口（Windows UIPI 限制）。

## 通过 Cloudflare Tunnel 发布到公网

需要先安装 [cloudflared](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/downloads/)（也可以把 `cloudflared.exe` 放在 ezcontrol.exe 旁边）。

**临时地址（无需账号）**：

```bash
ezcontrol.exe --tunnel
```

控制台会打印 `https://xxxx.trycloudflare.com` 公网地址，每次启动地址都会变。

**固定域名（推荐长期使用）**：在 Cloudflare Zero Trust 控制台 → Networks → Tunnels 创建隧道，Public Hostname 的服务填 `http://127.0.0.1:8090`，复制隧道 token 后：

```bash
ezcontrol.exe --tunnel-token <TOKEN>
```

也可以用你自己已有的 cloudflared 服务指向 `http://127.0.0.1:8090`，无需加参数。经隧道访问时，日志里记录的是 `CF-Connecting-IP` 头里的真实访客 IP。

如需更强的保护，可在 Cloudflare Access 给该域名再加一层邮箱验证。

隧道是否真的连通，以控制台为准：

- 连上后会打印「Cloudflare 隧道已连通，公网地址: …」。
- 如果 30 秒内连不上，会打印原因和处理办法。cloudflared 会继续在后台重试，连上后同样会提示。
- ezcontrol 退出（包括崩溃、被任务管理器结束）时，cloudflared 会被一并结束，不会残留。

### 打开公网地址显示 Error 1033

1033 表示这个地址没有任何 cloudflared 连接在线。常见原因：

1. **本机连不上 Cloudflare 边缘的 7844 端口。** 快速隧道的地址是通过 443 端口申请的，所以照样能拿到地址，但隧道本身走的是 7844 端口（UDP 走 QUIC，TCP 走 HTTP2）。
   - 本机开着代理/TUN（sing-box、Clash、xray 等）时，常见现象是 7844 端口被劫持：日志里出现 `x509: certificate has expired`。
   - 也可能是网络直接阻断。
   - 解决：在代理软件里给 `cloudflared.exe` 设为直连/绕过，或放行到 `198.41.192.0/24`、`198.41.200.0/24`（IPv6 `2606:4700:a0::/48`、`2606:4700:a8::/48`）的 7844 端口；也可以换一个网络。只有 UDP 被挡时，可以加 `--tunnel-protocol http2`。
2. **用的是旧地址。** 快速隧道每次启动地址都会变，ezcontrol 重启后旧地址就失效了。需要固定地址请用命名隧道（`--tunnel-token`）。

## 性能

测试本机的采集和编码能力：

```bash
ezcontrol.exe --bench
```

它会报告首帧耗时、3 秒内的采集帧率和编码管线帧率，以及整帧复制、缩放、差分、编码各环节的耗时。测试时让屏幕上有东西在动（比如播放视频），否则屏幕不变就没有帧可采。

工具栏上的 fps 是**实际发送的帧数**：画面不动时不发帧，显示 0 是正常的。

### 采集方式

`--capture` 可选 `auto`（默认）、`wgc`、`dxgi`、`gdi`。

| 方式 | 适用 | 说明 |
|---|---|---|
| `dxgi` | 有显卡的机器（`auto` 默认选它） | 只复制变化区域，开销最低 |
| `wgc` | 无显卡的虚拟机/云主机（`auto` 自动选它） | Windows 10 上屏幕边缘可能出现黄色采集边框，这是系统行为 |
| `gdi` | 兜底 | 最慢 |

### 实测（2550×1242，无显卡的云主机，8 核）

一个窗口持续动画时：

| | 采集帧率 | 编码耗时/帧 |
|---|---|---|
| 优化前（DXGI，同步读回 + 多次整帧拷贝） | 17–20 fps | — |
| DXGI（去掉整帧拷贝） | 17–20 fps | 约 3 ms |
| Windows.Graphics.Capture | 约 28 fps | 约 2.5 ms |

浏览器端到端约 22–25 fps，浏览器也开在同一台机器上，会占用一部分 CPU。

这台机器上的上限来自系统合成器：没有显卡时，DWM 用 CPU 合成整个桌面，大约每秒只产生 35–40 帧；DXGI 读回每帧还要等合成器约 40 ms。有显卡的机器上，DXGI 可以跑满 60 fps。

其他参考数据：

- 整屏 JPEG 编码 8 核并行约 11–14 ms，单线程约 40–56 ms。
- 日常局部变化帧平均几 KB 到几十 KB。

公网使用的调优建议：

- 带宽有限时调低画质，或把缩放调到 75% / 50%，对延迟和流畅度最有效。
- 帧率上限 60；网络不够时，ACK 流控会自动丢掉中间帧，保持最新画面。

### 编码：H.264 与 JPEG

工具栏「编码」可选：

- **H.264（默认）**：服务器用 openh264 编码，浏览器用 WebCodecs 硬件/软件解码。
  - 只传画面变化，同样画面的数据量约为 JPEG 的 1/5–1/12，慢速链路上画质和帧率都高得多。
  - 「画质」滑块决定码率上限，状态栏显示当前码率/上限。
  - 需要 HTTPS（例如经 Cloudflare 隧道访问）或 localhost，以及支持 WebCodecs 的浏览器：Chrome/Edge 94+、Safari 16.4+、Firefox 130+。
  - 用 http 加局域网 IP 访问时浏览器不提供 WebCodecs，会自动改用 JPEG。
- **JPEG**：分块差分，兼容所有浏览器，局域网里 CPU 延迟最低。

本机实测（2550×1242，一个窗口持续动画）：H.264 约 28–31 fps、约 0.85 Mbps；JPEG 约 22–25 fps、约 10 Mbps。

### 公网/高延迟网络

画面流按「每帧送达确认」做拥塞控制，按网络状况自动调节。

**拥塞控制：**

- 每帧被浏览器画出后会回一个确认，服务器据此测出每帧的往返时间。
- 往返时间持续高于基线，说明链路在排队，就减少在途数据；不排队时就放开。
- 小帧可以同时有很多在途，不会被往返时间卡住帧率。
- 偶发的网络抖动会被平滑掉，不会误判。

**自动画质（工具栏「自动」，默认开）：**

- 只有在画面产生的数据超过链路承载能力、出现排队时，才先降画质（最低 30）。仍不够时再降分辨率（75%、50%）。
- 通畅后逐步恢复。
- 工具栏的画质和缩放设置是上限。
- 降级时状态栏会显示「自动降至 画质…/…%」。

实测（经 Cloudflare 快速隧道，链路约 6.5 Mbps，基础往返约 560–600 ms）：

| | 帧率 | 延迟（中位） |
|---|---|---|
| 优化前 | 2–3 fps | 数秒 |
| 优化后，画面一般变化 | 约 25 fps | 约 600 ms |
| 优化后，大面积动画 | 15–25 fps，自动降画质 | 约 600–900 ms |

经同一隧道、链路只剩约 1.5 Mbps 时：JPEG 即使降到画质 30、缩放 50% 仍只有约 10 fps；H.264 以原分辨率约 20 fps，只用 0.5–1 Mbps。

剩下的延迟基本是网络本身：从国内经 Cloudflare 免费隧道绕到海外再回来，往返就要 0.5 秒以上，而且不同时段抖动很大。这部分只能靠更近的线路降低：局域网直连、国内中转服务器，或 P2P 组网工具。

### 诊断日志

所有日志同时写入 exe 旁的 `ezcontrol.log`（超过 5 MB 自动重写）。

每个远程会话每 10 秒记录一行「会话统计」，内容包括：

- 发送帧率、码率
- RTT（平滑值、基线、排队）
- 在途预算
- 带宽估计
- 拥塞次数
- 当前画质或码率

画面卡顿时看这一行就能判断：

- RTT 基线本身就很高，或带宽估计很低：瓶颈是网络。
- 拥塞次数多、预算很小：是流控在限速。

## 已知限制

- **Ctrl+Alt+Del、锁屏/登录界面、UAC 安全桌面**：普通进程无法采集或操作这些界面，Windows 的安全设计如此。打开任务管理器请用 Ctrl+Shift+Esc。
- 剪贴板只同步文本，不同步图片和文件；单次自动同步上限约 4M 字符。
- Firefox 不允许网页随时读取剪贴板，本机→远程的自动检测只在 Chromium 内核浏览器（Chrome、Edge）可用。
- 不传输声音。
- 屏幕旋转的显示器未做适配。
- 编码使用 JPEG，兼容所有浏览器、实现简单；如果以后需要更低带宽，可以考虑换 H.264 + WebCodecs。

## 构建

需要 Rust（MSVC 工具链）：

```bash
cargo build --release
```

产物：`target/release/ezcontrol.exe`。前端文件位于 `web/`，编译时嵌入 exe。

代码结构：

- `src/capture.rs`：屏幕采集（DXGI、GDI、帧缓冲池）
- `src/wgc.rs`：Windows.Graphics.Capture 采集
- `src/stream.rs`：画面差分、编码与 WebSocket 会话
- `src/h264.rs`：H.264 编码
- `src/pacer.rs`：拥塞控制
- `src/input.rs`：键鼠注入、剪贴板
- `src/files.rs`：文件接口
- `src/auth.rs`：登录鉴权
- `src/tunnel.rs`：Cloudflare 隧道
